## Цель

Сделать supplier-сторону пригодной для локально проверяемой работы: поставщик может заполнить и поддерживать профиль и каталог в рамках существующей модели данных, а уполномоченный оператор — рассмотреть профиль/каталожные данные и записать проверяемое решение. Не допустить самоподтверждения, утечки между tenant и ложного впечатления, что supplier прошёл реальные юридические или качественные проверки.

## Объём работ

1. Аудируй существующие supplier routes, profile/catalog repositories, permissions, CSV workflow и миграции. Зафиксируй, что уже работает, и добавляй только недостающие сценарии; не дублируй существующий import.
2. Заверши локальный supplier onboarding UX на существующих полях: создание/просмотр/редактирование профиля, ясный статус и следующий шаг, необходимые form validation и сохранение. Не выдумывай обязательные лицензии, реквизиты, страны, адресные форматы, юридические статусы или дополнительные проверки: такие решения открыты и должны быть переданы владельцу продукта.
3. Улучши управление каталогом: просмотр своих offers, создание и редактирование черновика, публикация/снятие с публикации только если это поддержано допустимым backend-контрактом, валидация упаковки/единиц, MOQ, order step, цены/валюты, availability и наблюдаемого времени. Не представляй supplier-reported availability как зарезервированный остаток.
4. Дополни существующий CSV preview/apply UX: понятные построчные ошибки, безопасный повтор и результат применения; серверная валидация остаётся источником истины. Повторный импорт не должен незаметно создавать дубли. Не меняй поддерживаемую CSV-схему без совместимого решения и тестов.
5. Создай локальную operator review queue для supplier profile/catalog, если можно использовать уже имеющуюся надёжную авторизационную модель. Показать pending/reviewed и точные действия/причины; поддержать approve/reject (или текущие эквиваленты) только серверным действием с append-only audit. Объяснить оператору, что решение — лишь внутренний статус прототипа, не юридическая сертификация или гарантия качества.
6. Для каждой роли отрази разрешённые действия. Supplier owner/admin и `catalog_operator` управляют только собственным tenant и офферами в разрешённом состоянии. Supplier не может повысить свой статус, одобрить себя или просматривать/изменять чужой профиль и каталог. Пользователь без назначенной операторской привилегии не должен видеть или выполнять глобальную moderation.
7. Сохраняй доступность форм, mobile layout, loading/empty/success/error states, локализацию и безопасные typed errors. Поддерживай существующие buyer offer visibility rules.

## Безопасность и инженерные ограничения

- Все проверки tenant, роли и конкретного объекта выполняются сервером (RLS/grants/RPC/repository); клиентские guard/filter — только UX.
- Операторская полномочность не должна определяться непроверяемым query string, редактируемым user metadata, client flag или demo persona. Если база не предоставляет безопасный способ определить platform moderator, не добавляй глобальный доступ «для удобства»: подготовь предложение по минимальному role/authorization contract и вынеси блокер.
- Любая новая схема — отдельная supplier-domain миграция с минимальными grants и deny-by-default; таблицы не открывать автоматически через Data API. Пиши негативные RLS/role tests для чужого tenant и неавторизованного оператора.
- Catalog price/availability имеют отдельные timestamps; stale/unknown значения не маскируй как актуальные. Не конвертируй валюты и не придумывай коммерческие условия.
- Сохраняй безопасную CSV обработку: ограничение размера/строк, текстовая обработка, серверная повторная валидация, без исполнения формул/макросов и без тихого исправления данных.
- Аудит неизменяем; исправление ошибки — компенсирующее событие, не редактирование истории.
- Не редактируй generated `src/data/supabase/database.types.ts` параллельно с Task 3. Подготовь миграцию и typed contract для последующей интеграции/review.

## Границы ответственности и зависимости

**Этот поток владеет:** supplier profile/onboarding, catalog authoring/import UX и moderation этих сущностей. Buyer/account UX принадлежит Task 1. Приём, отклонение и предложение условий по buyer request / supplier suborder принадлежат Task 3; не реализуй supplier order inbox, order response или принятие покупателем новой версии условий.

Уже имеющийся CSV import и существующие offer snapshots — не повод менять формат или поведение buyer request. Не меняй атомарный submit, private supplier suborders, request snapshots или lifecycle подзаказов. Если для supplier moderation отсутствует нужный backend-контракт, покажи точный пробел вместо клиентской имитации.

## Критерии приёмки

- Поставщик может локально заполнить и сопровождать только собственный профиль и каталог с честным статусом проверки.
- Поставщик не может назначить себе approved/verified; pending не отображается buyer-у как одобренный поставщик.
- Только проверенная серверная operator role может принять moderation decision; все действия привязаны к действующей организации/объекту и журналируются append-only.
- Негативные тесты подтверждают отказ чужому supplier tenant и неавторизованному operator; чужие данные не раскрываются по подставленному ID.
- Offer UI корректно показывает sell unit/pack, MOQ/step, currency и раздельную свежесть price/availability; неизвестные/устаревшие условия не выглядят валидными.
- CSV preview и apply остаются согласованными, сервер повторно валидирует, повтор не дублирует данные; ошибки можно исправить без потери контекста.
- Buyer visibility по-прежнему ограничена опубликованными offers одобренных suppliers; buyer-request flow и его snapshots не изменены.
- Новые миграции безопасны, имеют релевантные pgTAP tests и не расширяют публичную поверхность без необходимости.
- Результаты тестов и среда описаны точно; никакие действия не выполнялись на hosted/production сервисах.
