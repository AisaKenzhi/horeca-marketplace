# ORDER-01 — локальная граница «request ≠ заказ»

**Решение агента (обратимое, по разрешению владельца работать без вопросов):** в текущем прототипе нет статуса подтверждённой закупки. Ответ поставщика и решение покупателя меняют только workflow-ветку; родительский buyer request остаётся `submitted`. Принятие условий не создаёт заказ, оплату, счёт, резерв или доставку.

Это граница локального среза, а не коммерческая/юридическая модель пилота.

## State table (текущий контракт)

| Объект                   | Статусы                                                                                                                      | Что НЕ следует из статуса                                    |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Parent buyer request     | `submitted`                                                                                                                  | принятый заказ, оплата, резерв, отгрузка                     |
| Supplier workflow branch | `awaiting_supplier`, `supplier_accepted`, `supplier_rejected`, `awaiting_buyer_decision`, `buyer_accepted`, `buyer_rejected` | подтверждённая покупка, invoice, stock reservation, delivery |
| Terms version            | `1..n`, каждая immutable                                                                                                     | разрешение перезаписать исходный snapshot                    |

Никакой статус workflow не содержит `order/paid/reserved/delivered/invoice` — это проверено domain-тестом. Решения buyer принимают **точную** `termsVersion` с `expectedVersion`; повтор идемпотентен.

2. Что происходит с 다른 ветвями при частичном принятии/отмене?
3. Кто владеет статусами cancellation, fulfillment, receipt и payment?
4. Какие причины, таймауты и компенсирующие действия требуются?

## Граница

local/ephemeral CI на синтетических данных. Никаких реальных заказов, платежей, reservation, уведомлений, hosted DB или deploy. См. `blocker-decision-briefs.md` (ORDER-01).
